## 1. What this project is

A prototype for the NIT Tiruchirappalli CDI internship task: an order-to-audit system for a small South Indian snack factory.
Two loops meet at finished-goods (FG) stock:

- **Sales loop:** order, admin verification, GST invoice, dispatch (FG goes down), payments and outstanding.
- **Production loop:** purchase, raw stock, issue against a BOM, production run (FG goes up), variance and cost per packet.

Priority when trade-offs appear: (1) correct benchmark numbers, (2) ledger-based stock and BOM variance logic, (3) sales-to-invoice flow, (4) code quality and tests, (5) usability, (6) reports and docs, (7) stretch features.
A smaller system that passes the benchmark beats a bigger one that does not.

Source of truth, highest first: Appendix A (benchmark) > this file > `docs/DESIGN.md` > code comments.

## 4. Domain invariants (hard rules)

1. **Decimal only.** Money and quantities are `Decimal`. NEVER `float` anywhere in backend money or stock code. Quantities are NUMERIC(14,3) in the item's base unit (kg, L, piece, packet). Money is NUMERIC(14,2). Rates are NUMERIC(14,4). Round only with `core.money.q2()` (ROUND_HALF_UP). The API serialises decimals as strings. The frontend never does money arithmetic; it displays server values (`Intl.NumberFormat('en-IN')`).
2. **Services own mutations.** Every write to stock, ledger, invoices, payments or production goes through a `services.py` function decorated `@transaction.atomic`. Views, serializers, admin and management commands call services. They never write those tables directly.
3. **Ledger is append-only.** `stock_ledger` rows are never updated or deleted (a database trigger enforces this). Corrections are reversing entries. Opening balances are `OPENING` ledger rows. `stock_balance` is updated in the same transaction under a row lock, with `CHECK (qty >= 0)`, and must always equal `SUM(ledger)`.
4. **Traceability.** Every ledger row has non-null `source_type` and `source_id` (purchase, production run, invoice or dispatch, adjustment, credit note, opening).
5. **Valuation is moving weighted average**, behind a strategy class so FIFO can be swapped in. Issue value = `q2(issue_qty * running_value / running_qty)`. The balance keeps the remainder, so issuing all remaining quantity leaves value exactly zero.
6. **Variance flag** when `abs(actual - planned) / planned > tolerance`, strictly greater than, both directions, tolerance from settings (default 3%). Record direction (favourable or adverse). Variance is computed once at run completion and stored as a snapshot. Later BOM edits never change past runs.
7. **BOM is versioned.** A run references a BOM version and copies planned quantities.
8. **GST.** Place of supply = customer state vs factory state (Tamil Nadu, code 33). Same state: CGST + SGST, half each. Different: IGST. Tax is rounded half-up per line to paise, with round-off shown separately. HSN and rate live on the product.
9. **Invoices are immutable once posted** (trigger enforced). Cancel with a credit note, never delete. Numbering `INV/26-27/00001` and `CN/26-27/00001` (maximum 16 characters), a per-financial-year counter taken under a row lock. The financial year starts 1 April and is computed in Asia/Kolkata. Store timestamps in UTC.
10. **Audit log in the same transaction.** Edits to orders, invoices and production runs write `audit_log(user, ts, entity, id, action, before, after)` inside the same transaction as the change.
11. **Concurrency.** Lock `stock_balance` rows in ascending item-id order. Two simultaneous dispatches of the last stock must not both succeed.
12. **RBAC is server-side and deny-by-default.** Roles: salesman, admin, production, accountant (read-only), owner. A salesman sees only their own orders and assigned customers. Frontend hiding is cosmetic only.
13. **Idempotent order submit.** `POST /orders` requires a client UUID. A retry returns the existing order and never creates a duplicate.
14. **No hard deletes** of business documents (orders, invoices, runs, payments, purchases).
15. **Seed is idempotent.** `seed_benchmark` loads Appendix A master data and supports `--reset`.

## 5. Testing rules

**Process.** Red, green, refactor. Write the failing test first, then the code, and commit them together.
Tag each test with the requirement it covers in its docstring, for example `PS 4.3 variance flag`.

**Layers.**

- **Unit** (pure functions, no DB): variance, GST, valuation, unit conversion, rounding.
- **Integration** (real PostgreSQL, services): ledger, production, sales, payments, costing.
- **API** (DRF client): every endpoint tested for each allowed role and at least one denied role.
- **E2E** (Playwright): salesman order flow, admin approval to invoice to dispatch, production run screen, offline queue and sync.
- **Benchmark**: `backend/tests/benchmark/test_benchmark_end_to_end.py` replays Appendix A steps through the services and asserts every expected value. Treat it as sacred.

**Property-based tests (hypothesis) are required for:**

- Any sequence of valid movements keeps `balance == SUM(ledger)`, `qty >= 0`, and value 0 when qty is 0.
- `taxable + cgst + sgst == total` and `taxable + igst == total`, with no paisa lost.
- Unit conversion round trips are exact for 3-decimal quantities.

**Required test cases per area:**

- Variance: exactly at tolerance (not flagged), just over (flagged), favourable and adverse, zero planned quantity.
- GST: intra-state, inter-state, rounding edge, 1 April FY rollover (freezegun), 16-character invoice number limit.
- Database: UPDATE or DELETE on `stock_ledger` and on a posted invoice raises. Negative stock is rejected.
- Concurrency: two parallel dispatches of the last packets, exactly one succeeds.
- RBAC: a role by endpoint matrix, and a salesman cannot read another salesman's orders.

**Forbidden test practices:**

- Editing expected values in Appendix A, or weakening an assertion, to make a test pass. If you believe a test or an expected value is wrong, stop and ask.
- `skip`, `xfail` or deleting a test without owner approval.
- Mocking the database, or mocking the service under test. Use real PostgreSQL.
- Float assertions. Compare `Decimal` values.
- `sleep` calls, and tests that depend on wall-clock time or on test order.
- Building state by inserting rows directly when a service exists. Use the service (low-level ledger tests are the exception).

**Mutation sanity check.** After writing a test for critical logic (valuation, variance, tax, stock checks), break the code once on purpose and confirm the test fails. Then restore it.

**Coverage gate.** At least 80% overall, and at least 90% on `core/` and every `services.py`. CI fails below this.

## 6. Verification protocol (definition of done)

A feature is done only when all of the following hold. "It should work" is never evidence.

1. Acceptance criteria exist as tests that were written first and now pass.
2. `make check` passes (lint, types, unit, integration, API, coverage gate).
3. `make benchmark` passes every check. Run it before every PR, and always after touching stock, production, billing, payments, costing or reports.
4. Exercised for real against the running stack (`make up`): new endpoints called with curl or httpie, new screens driven by Playwright with a screenshot saved to `docs/evidence/<feature>.png`.
5. For anything with stock or money effects, query the database and report the actual ledger rows and audit rows produced.
6. Negative paths verified: insufficient stock, wrong role, duplicate submit, invalid unit, bad GSTIN, posted-invoice edit.
7. `make reconcile` passes: balance equals ledger sum, invoice totals equal line sums, sales register taxable total equals GST summary taxable total.
8. Full suite passes, not only the new tests.
9. README feature matrix and assumptions are updated if behaviour or an assumption changed.

## 7. Workflow and git

## 8. Code conventions

- Backend: type hints on all services, a docstring on each service stating the invariants it protects, no business logic in views or serializers.
- Errors: raise `core.errors.DomainError` subclasses (`InsufficientStock`, `InvalidUnit`, `InvoiceImmutable`, and so on), mapped to 4xx responses with machine-readable codes.
- Frontend: typed API client, server state in TanStack Query, mobile-first screens for the salesman (touch targets at least 44 px), tablet-friendly production screen with large numeric inputs.
- All user-visible strings go through react-i18next (`en`, `ta`). No hard-coded strings in components.
- No magic numbers. Tolerance, factory state code and similar values come from settings.

## Appendix A: Benchmark ground truth

**Never edit these values to make a test pass.** Seed users: salesman_a, salesman_b, admin, production, accountant, owner.

### Master data

Factory: Tamil Nadu (state code 33). Retailer A: Tamil Nadu. Distributor B: Karnataka (state code 29). Selling price for Murukku 200 g: ₹50 before tax, GST 5%. Variance tolerance 3%.

BOM for Murukku 200 g, one batch = 200 packets expected (assumption: bulk output 40 kg, pack size 200 g):

| Item | Qty per batch | Unit | Rate (₹) |
| --- | --- | --- | --- |
| Flour | 40 | kg | 42 opening stock, 45 new purchase |
| Cooking oil | 10 | litre | 140 |
| Salt and spice mix | 1.2 | kg | 200 |
| 200 g pouch | 200 | piece | 2.50 |
| Carton (holds 20 packets) | 10 | piece | 15 |

Opening stock: flour 100 kg, oil 30 L, spice mix 5 kg, pouches 500, cartons 30, finished Murukku 200 g 50 packets.
Assumption to document in README: opening FG is valued at standard material cost, ₹19.85 per packet (3,970 / 200).

### Steps

1. Purchase 60 kg flour at ₹45/kg.
2. Production run, 1 batch: issue 40 kg flour, 10.5 L oil, 1.2 kg spice mix.
3. Actual output 188 good packets, 6 pouches damaged, 9 cartons used.
4. Salesman A orders 150 packets for Retailer A.
5. Admin approves, raises GST invoice (CGST + SGST), records dispatch.
6. Salesman B orders 120 packets for Distributor B. Insufficient stock.
7. Payment of ₹4,000 from Retailer A.
8. Add labour ₹1,200 and gas/power ₹600 to the run. Show cost per packet.
9. Generate the month's reports.
